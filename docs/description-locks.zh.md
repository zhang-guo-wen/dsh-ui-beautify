# 描述翻译跨进程锁

[English](<description-locks.md>)

## 安全约定

锁仅协调**同一本机文件系统、同一 PID 命名空间**中的宿主。并发写入者必须全部使用本协议；升级前停止旧宿主。PID 复用、进程探测权限不足均视为存活／未知，不作为死亡证据。这不是分布式锁，也不防御恶意进程任意改写数据目录。

记录 key 是 `description-translations/v1` 下的 SHA-256 文件名。锁必须为非符号链接的真实目录，且仅包含一个零字节普通文件 `PID.UUID.owner`。未知文件、旧版空锁、畸形标记及符号链接锁均保留；等待仍受请求取消／超时约束。

## 发布与真正单赢家回收

1. 在旁路唯一目录 `.lock.candidate-PID.UUID.owner` 内初始化 owner，再以一次目录 rename 发布至 `.lock`。协议参与者只发布**非空**目录，竞争发布不能替换已有锁。发布前崩溃只留下无阻塞的候选元数据，不会留下 canonical 空锁。
2. 释放与恢复统一将整个 canonical 锁目录 rename 为 `.lock.retired-PID.UUID.owner`。恢复要求 `kill(pid, 0)` 明确返回 `ESRCH`，且在 rename 前及每次重试前重新验证精确 owner。正常释放使用**相同**目标路径。
3. retired 目录永久保持非空。即使第二观察者在验证后暂停，直到另一进程完成回收并取得新锁才恢复，rename 也不能覆盖旧世代的非空栅栏。因此每个世代只有一个回收赢家。回收 rename 后立即崩溃，canonical 路径已经可用，无需等待回收 claim 租约过期。
4. 不 unlink canonical owner，也不 rmdir canonical 目录。Windows 可能将同一 owner 的两个并发 unlink 都报告为成功，不能用它选主。
5. Windows rename 的 `EPERM`／`EACCES`／`EBUSY` 在首次失败后最多重试四次、间隔 25ms。持续失败保持 fail-closed，不绕过权限。获取／写入失败可报告存储错误；已落盘的批量结果或已取消请求之后的清理失败可能留下 live-PID 锁，直到持有进程退出，且不改变已返回的结果。已知存活锁的等待仍由请求 deadline 限定。

## 元数据保留与维护

每次实际取得锁保留一个小目录及空 owner 文件。初次查询命中缓存不占锁；等待者取得锁后才发现缓存时仍增加标记；失败／取消的生成尝试可能增加标记。发布前崩溃还可能留下候选目录。这些是有意保留的安全元数据，不是译文缓存。

**任何共享宿主或暂停的锁观察者仍在运行时，不得删除 retired 栅栏。** 删除会重新开放 ABA 竞态。需要清理时，先停止共享该数据目录的全部宿主、确认观察者均退出、备份目录，再人工核对精确生成路径。插件不会递归删除或扫描无关目录。旧版未知锁需人工调查，不能按年龄自动删除。

## 回归证据

`tests/description-process-lock.test.mjs` 在真实子进程的文件系统 rename 边界设置屏障：只有另一进程完成旧锁回收并取得新锁，暂停的旧回收者才恢复。另覆盖发布前后崩溃、回收／释放 rename 后立即崩溃、token 替换、未知／畸形标记、存活锁取消、忽略取消的生成，以及注入的 Windows sharing violation 有界重试。重复双宿主孤儿锁竞态仅为确定性测试的补充，不替代它们。
